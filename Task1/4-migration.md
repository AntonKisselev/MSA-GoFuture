## План миграции данных
   
- Создание новой схемы БД для сервиса. Проектирование с учетом доменной модели. 
- Настройка конвейера данных для однократной загрузки исторических данных из монолита в новую БД с помощью ETL-процессов. И для дальнейшей поддержания актуального состояния, то есть, где большой объем данных например геоданные то можно перенос данных вести фоном, параллельно с дальнейшими шагами 
- Использование паттерна "Outbox" в монолите для надежной отправки событий в Kafka, которые будет потреблять новый сервис для поддержания своей БД в актуальном состоянии. Это избегает прямых транзакций между разными БД.
- Канареечное тестрование новой БД. Настроить API Gateway так, чтобы небольшой процент трафика (1-5%) на чтение данных направлялся в новый сервис, а ответы сравнивались с ответами монолита.
- Постепенно увеличивать процент трафика до 100%.
- После успешного переноса и проверки целостности, переводим запись напрямую в новую БД, а для монолита используем подписную модель Kafka
- Когда новый сервис стабильно обрабатывает 100% трафика в течение нескольких недель, код, отвечающий за данный домен, удаляется из монолита.
- Старые таблицы в основной БД монолита архивируются, но не удаляются немедленно.
